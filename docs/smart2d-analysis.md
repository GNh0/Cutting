# Smart2DCutting 설치본 REA·Ghidra 분석

2026-10-23. 대상은 설치된 `Smart2DCutting 3.5 Demo`의 `Smart2DCuttingDEMO.exe`이다. **프로그램 전체 소스나 최적화 수식을 동일하게 복구한 결과는 아니다.** 초기 `smart2d-v1` 등록은 공개 실행 계약을 참고한 별도 휴리스틱이었다. 이번 수정은 그 휴리스틱을 설치본에서 확인한 반복 배치·분할·잔재 병합 기준으로 교체한다.

## 도구 설치와 확인

- 공식 출처는 [morluto/rea](https://github.com/morluto/rea), 최신 릴리스는 [rea-agents 6.7.0](https://github.com/morluto/rea/releases/tag/rea-agents-6.7.0)였다. 실제 설치한 패키지와 `rea --version` 모두 6.7.0이다.
- REA의 지원 범위에 맞춰 공식 Ghidra 12.1.4와 Temurin JDK 21을 설치하고 다운로드 체크섬을 검증했다. 최신 Ghidra 전체 버전을 임의로 택하지 않고 REA가 지원하는 12.1.x를 사용했다.
- REA 고정 설치 경로는 `C:\Users\KONEIT\.local\share\rea`이다. Codex MSIX 가상 npm 경로로의 영구 등록은 REA가 거부해 고정 경로를 사용했다.
- Codex 설정 백업은 `C:\Users\KONEIT\.codex\config.toml.rea.backup`이며 기존 설정을 보존한 채 REA 등록과 대응 스킬을 추가했다. setup 결과는 `ready`, doctor는 `healthy: true`, 사용 가능 provider는 `ghidra`였다. 현재 열린 Codex에 자동으로 새 도구가 주입되는 것은 아니므로 이번 작업에서는 별도 CLI/MCP 세션도 사용했다.

## 설치 파일과 정적 분석

원본 SHA-256: `8c5361f92ee94aa4d813d53806c834d9ce10eb660f925b9136de8bbd577a50e4`.

REA의 `analyze ... --provider ghidra --json`을 실제 실행했다. Evidence ID는 `ev_7629addd367778647689e47f91fc47952f0fdc41888a6e72d0e3842fe0985902`이다. Ghidra 12.1.4는 x86 PE, 이미지 기준 주소 `0x400000`, 섹션 11개(헤더 포함), 정의된 함수 34개와 문자열 5,777개를 보고했다. 원본 진입점과 `.smrfdky` 영역, 압축된 코드 구조 때문에 이 숫자를 프로그램 전체 함수 수로 해석하지 않는다.

실행 파일을 패치하지 않고 작업 전용 프로세스를 정상 시작해 이미지 메모리를 읽었다. 7,561,216바이트의 이미지에서 읽지 못한 페이지는 없었다. 프로그램의 원래 섹션 매핑으로 분석용 사본을 만들었으며, 그 SHA-256은 `279fed951b4c369a80d35e065309ed9bb4313e0ff2c282abc816eb232f50585e`이다. 이 사본은 원본 파일이나 원래 소스가 아니며, 런타임에 채워진 포인터와 초기화 데이터가 포함된다. 프로그램 데이터와 데모 제한은 패치하지 않았다.

시작 도중 사용자가 `PANELS.DBF` 생성 오류를 보고했다. 파일과 기존 데이터의 존재 및 폴더 권한은 확인했지만 원인을 확정하지 않았다. 추가 실행을 중단하고 이미 확보한 사본만 분석했다. 이 때문에 원본 프로그램을 같은 복합 입력으로 정상 계산시킨 비교는 수행하지 않았다.

## Ghidra에서 확인한 경로

사본의 REA 전체 자동 분석은 330초 시작 제한을 초과했다. 제한을 숨기거나 성공으로 처리하지 않았다. 이후 Ghidra headless의 `-noanalysis`와 작업 전용 Java 스크립트로 선택한 함수만 역어셈블·역컴파일했다. 언어는 `x86:LE:32:default`, 컴파일러 규약은 `borlandcpp`였다.

| 위치 | 확인한 내용 | 해석 범위 |
|---|---|---|
| VCL 메서드 표 → `0x40e218` | `OptimizareF71Click` 메서드 주소, UI 선택 인덱스와 분기, 입력 검사 및 실행 경로 호출 | 최적화 버튼 진입 경로 |
| `0x4b3440` | 두 UI 선택 값의 전체 선택 분기, 3회/9회 결과 표 구성, 전역 선택 값 저장·변경·복원, 계산 진입 함수 호출 | 공식 도움말의 방향 3종 × 수준 3종과 부합하는 후보 실행 제어 |
| `0x4b6cb0` | 파일 경로 구성과 기존 결과 파일 정리, 3×3 이름 순회 | 계산식으로 오인하지 않고 결과 정리 경로로 분리 |
| `0x4a1dac` | 데이터셋·입력 검사와 여러 경고 경로 | 입력 검증 경로, 알고리즘 핵심 수식으로 단정하지 않음 |
| `0x405ca4` → `0x4063d4` | 데이터셋 순회·수치 필드 처리와 후속 경로 | 보조 계산과 제어 흐름의 일부. 타입·함수 경계·간접 호출 복구 한계가 있음 |

역컴파일이 완료됐다는 것은 복구된 표현을 얻었다는 뜻이다. 원래 타입, 함수 경계, 동적 호출과 분기 의미를 모두 증명하지 않는다. 일부 함수에서 checksum 형태의 분기와 무한 루프 경고가 남아 있어 해당 표현을 원본 알고리즘의 완전한 의사 코드로 사용하지 않았다. 보호·라이선스·데모 검사를 우회하거나 수정하지 않았다.

공식 도움말과 설치 readme에서 확인한 외부 설정은 [동작 계약](smart2d-contract.md)에 따로 정리했다. 이 초기 분석만으로 내부 정렬·점수·동률 규칙을 복구했다고 보지 않는다. 뒤의 추가 분석에서 직접 확인한 기준과 남은 한계를 구분한다.

## 계산 후 이미지의 추가 Ghidra 분석과 이식

사용자가 이미 계산한 프로그램의 메인 이미지에서 읽기 전용 사본을 확보했다. 원본 실행 파일, 프로그램 메모리, DBF 데이터와 데모 제한을 수정하지 않았다. 분석 사본 SHA-256은 `6c22e6bed6ef6468d75d094725895c8429a307af8e17f9251fc85f304a05c068`이며 시작 시점의 앞선 사본과 다르다. 새 REA Evidence ID를 발급한 것처럼 처리하지 않고 직접 Ghidra 집중 분석 결과로 구분한다. 사용자 프로그램은 종료하지 않았고 분석용 headless 프로세스는 종료를 확인했다.

| 함수 | 직접 확인한 계약 | 구현 |
|---|---|---|
| `0x43ed38` | 원래 부재 면적 내림차순, 같은 면적은 기존 행 앞에 삽입 | 그룹 정렬 |
| `0x594cc8`, `0x5952f4` | 가로/세로 축에 같은 부재를 여러 개 반복하는 충전율 비교 | 반복 배치 코어 |
| `0x57df6c`, `0x57daf4` | 가로 줄/세로 열 배치 후 두 잔여 영역 생성 | 두 분할 구조 |
| `0x593e1c`, `0x58551c`, `0x592278` | 잔여 치수·좌표 직접 저장, 양수/원판 경계 검사, 부재 생성과 수량 차감 | 치수와 위치 생성 |
| `0x57cbd0`, `0x57c354` | 원판 아래/오른쪽에 붙은 잔여의 병합, 75% 비율과 강제 병합 분기 | 절단 전 계획 영역의 병합 |
| `0x57d73c`, `0x57d524` | 기존 계획 절단선 끝점과 플래그를 통한 병합 허용 검사 | 계획 절단선 목록을 별도 유지 |
| `0x57a9c0`, `0x57b494` | 방향 접두 경로를 재생하고 두 완성 배치의 이용률·최대 잔재 비교 | 상위 수준의 접두 경로 탐색 규칙 |
| `0x4c3de4`, `0x58810c`, `0x7a8010`, `0x7a8cf0`, `0x7a81e4` | 활성 부재의 최대 입력 폭, 원판 장변/입력 폭의 올림, 최솟값 2 | 큰 부재 조기 종료 계수 |
| `0x57bf68`, `0x57d45c`, `0x57c028` | 부재 면적/전체 면적, 재사용 잔재 합/최대 잔재 비율 | 평가 항목 확인 |

반복 수는 `n = min(남은 수량, floor((영역 축 길이 + kerf) / (부재 축 길이 + kerf)))`이다. 평가용 채움 길이는 `n × (부재 축 길이 + kerf)`이고 영역 길이 이상이면 kerf 하나를 뺀다. 채움 길이/영역 축 길이 비율이 더 큰 후보를 채택하며 엄격한 `>` 비교라 준비된 부재/회전 순서가 동률 결과에 영향을 준다. 회전 후보를 먼저 검사하며 전역 허용·부재별 허용·Cutting의 결 방향 제약을 함께 적용한다. 충전 임계값에 도달하면 남은 부재 검사를 조기 종료하는 경로도 이식했다. 큰 부재 계수는 `max(2, ceil(원판 사용 영역의 장변 / 최대 입력 폭))`이다. 개별 회전이 허용된 부재는 원래 두 치수 중 큰 값을 입력 폭으로 사용하며, 활성 수량이 있는 현재 재질 부재만 고려하는 원본 경로를 확인했다. 올림은 x87 제어 비트와 `FRNDINT` 경로로 검증했다.

### 물리 절단 표현의 경계

원본은 끝부분에 kerf 전체가 남지 않아도 부재를 허용하고, 계획상의 절단선은 kerf 폭을 가진 직사각형이 아닌 끝점 쌍으로 보관한다. Cutting은 절단마다 실제 재료 안에서 소모되는 폭을 `kerf`, 전체 톱날 두께를 `nominalKerf`로 구분한다. 예를 들어 1168×1554 영역에 1168×120 부재 12개와 톱날 10mm를 배치할 때, 끝 절단은 판 안의 4mm만 소모한다. 그 4mm를 잔재로 중복 합산하지 않는다.

원본 잔여 병합은 이미 자른 두 조각을 붙이는 작업이 아니다. 절단 전 계획을 바꾸므로 병합 뒤 새 부재 좌표를 얻으면 길로틴 절단 트리를 처음부터 재구성한다. 해당 물리 검증에 실패하거나 병합이 추가 부재를 얻지 못하면 병합 전의 안전한 배치를 유지한다. 현재 재구성은 48개 이하 부재, 6000개 탐색 상태 한도이며 그 이상에서는 안전한 이전 계획으로 돌아간다. 이 한도는 원본의 내부 한도라는 뜻이 아니다.

### 등록 버전과 검증 범위

기존 저장 프로젝트의 `smart2d-v1` ID는 유지하고 표시 이름은 `Smart2D 배치 v2 (실험)`으로 변경한다. 예전의 임의 정렬 교란과 면적·절단 가중치 점수는 이 버전의 배치 코어에서 제거했다. 빠르게 9개·균형 36개·정밀 144개 방향·수준·충전 임계값 프로필을 비교한다. 각 프로필 내부의 방향 시험과 물리 절단 재구성은 별도이며, 이 숫자는 평균 실행 횟수도 원본 1~100 임계값의 전수 실행 횟수도 아니다.

첨부 화면의 **원본 첫 장에 표시된 24개**를 2500×2000 원판 1장, 톱날 10mm, 회전 끔으로 검증했다. 전부 배치되며 전체 부재 면적은 4,416,248mm²이다. 절단을 순서대로 재생해 부재·잔재·톱날 소모가 실제 최종 조각과 일치하는지 검사한다. 이 사례는 원본 전체 작업 입력을 복구했다거나 모든 좌표가 원본과 일치한다는 증거가 아니다.

결정트리 v3는 1·2번의 완성 결과를 선택하거나 조합하지 않는다. 부재 종류·배치 위치·회전·가로/세로 분할·새 원판 사용을 직접 분기해 완성된 배치의 부재 충족도·이용률·폐기 로스를 비교한다. Smart2D 반복 충전율을 3번의 배치 기준으로 복사하지 않는다. 공통 재질·재고·물리 절단 검증만 공유한다. 세 시작 경로와 개선된 완성 배치의 후속 분기를 예산 안에서 탐색한다. 분기 순서에는 격자 수용량의 휴리스틱 추정과 최대 16개 제약 부재 검사를 사용하지만 실제 배치 허용은 매번 물리 분할로 판정한다. 회전을 섞으면 단일 격자보다 더 들어갈 수 있으므로 이 추정값으로 배치 가능성을 배제하지 않는다. 탐색 한도 내 최선 결과이지 전역 최적해의 증명은 아니다.

### 아직 동일 복구가 검증되지 않은 부분

- 원본 정수 길이 단위와 입력 변환 정밀도 전체. 현재 포트는 Cutting의 mm 값을 사용한다.
- 원본의 전체 회전 재시도 상태 및 모든 UI 옵션 조합.
- 원본 DBF 작업의 원판 선택과 Cutting의 제조사·LOT 공유 재고 연결은 서로 다른 데이터 모델이다.
- 원본 실행 파일을 모든 무작위 입력으로 자동 실행한 쌍 비교는 수행하지 않았다. 브라우저 1·2·3번의 비교와 원본 프로그램 실행 비교를 혼동하지 않는다.

원본 EXE·메모리 사본·역컴파일 소스·사용자 데이터를 사이트에 배포하지 않는다.
