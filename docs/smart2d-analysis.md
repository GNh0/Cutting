# Smart2DCutting 설치본 REA·Ghidra 분석

2026-10-23. 대상은 설치된 `Smart2DCutting 3.5 Demo`의 `Smart2DCuttingDEMO.exe`이다. **프로그램 전체 소스나 최적화 수식을 동일하게 복구한 결과는 아니다.** 확인한 후보 실행 계약을 참고한 독립 엔진을 Cutting의 `smart2d-v1`으로 등록했다.

## 도구 설치와 확인

- 공식 출처는 [morluto/rea](https://github.com/morluto/rea), 최신 릴리스는 [rea-agents 6.7.0](https://github.com/morluto/rea/releases/tag/rea-agents-6.7.0)였다. 실제 설치한 패키지와 `rea --version` 모두 6.7.0이다.
- REA의 지원 범위에 맞춰 공식 Ghidra 12.1.4와 Temurin JDK 21을 설치하고 다운로드 체크섬을 검증했다. 최신 Ghidra 전체 버전을 임의로 택하지 않고 REA가 지원하는 12.1.x를 사용했다.
- REA 고정 설치 경로는 `C:\Users\KONEIT\.local\share\rea`이다. Codex MSIX 가상 npm 경로로의 영구 등록은 REA가 거부해 고정 경로를 사용했다.
- Codex 설정 백업은 `C:\Users\KONEIT\.codex\config.toml.rea.backup`이며 기존 설정을 보존한 채 REA 등록과 대응 스킬을 추가했다. setup 결과는 `ready`, doctor는 `healthy: true`, 사용 가능 provider는 `ghidra`였다. 현재 열린 Codex에 자동으로 새 도구가 주입되는 것은 아니므로 이번 작업에서는 별도 CLI/MCP 세션도 사용했다.

## 설치 파일과 정적 분석

원본 SHA-256: `8c5361f92ee94aa4d813d53806c834d9ce10eb660f925b9136de8bbd577a50e4`.

REA의 `analyze ... --provider ghidra --json`을 실제 실행했다. Evidence ID는 `ev_7629addd367778647689e47f91fc47952f0fdc41888a6e72d0e3842fe0985902`이다. Ghidra 12.1.4는 x86 PE, 이미지 기준 주소 `0x400000`, 섹션 11개(헤더 포함), 정의된 함수 34개와 문자열 5,777개를 보고했다. 원본 진입점과 `.smrfdky` 영역, 압축된 코드 구조 때문에 이 숫자를 프로그램 전체 함수 수로 해석하지 않는다.

실행 파일을 패치하지 않고 작업 전용 프로세스를 정상 시작해 이미지 메모리를 읽었다. 7,561,216바이트의 이미지에서 읽지 못한 페이지는 없었다. 프로그램의 원래 섹션 매핑으로 분석용 사본을 만들었으며, 그 SHA-256은 `279fed951b4c369a80d35e065309ed9bb4313e0ff2c282abc816eb232f50585e`이다. 이 사본은 원본 파일이나 원래 소스가 아니며, 런타임에 채워진 포인터와 초기화 데이터가 포함된다. 프로그램 데이터와 데모 제한은 패치하지 않았다.

시작 도중 사용자가 `PANELS.DBF` 생성 오류를 보고했다. 파일과 기존 데이터의 존재 및 폴더 권한은 확인했지만 원인을 확정하지 않았다. 추가 실행을 중단하고 이미 확보한 사본만 분석했다. 이 때문에 원본 프로그램을 같은 복합 입력으로 정상 계산시킨 비교는 수행하지 않았다.

## Ghidra에서 확인한 경로

사본의 REA 전체 자동 분석은 330초 시작 제한을 초과했다. 제한을 숨기거나 성공으로 처리하지 않았다. 이후 Ghidra headless의 `-noanalysis`와 작업 전용 Java 스크립트로 선택한 함수만 역어셈블·역컴파일했다. 언어는 `x86:LE:32:default`, 컴파일러 규약은 `borlandcpp`였다.

| 위치 | 확인한 내용 | 해석 범위 |
|---|---|---|
| VCL 메서드 표 → `0x40e218` | `OptimizareF71Click` 메서드 주소, UI 선택 인덱스와 분기, 입력 검사 및 실행 경로 호출 | 최적화 버튼 진입 경로 |
| `0x4b3440` | 두 UI 선택 값의 전체 선택 분기, 3회/9회 결과 표 구성, 전역 선택 값 저장·변경·복원, 계산 진입 함수 호출 | 공식 도움말의 방향 3종 × 수준 3종과 부합하는 후보 실행 제어 |
| `0x4b6cb0` | 파일 경로 구성과 기존 결과 파일 정리, 3×3 이름 순회 | 계산식으로 오인하지 않고 결과 정리 경로로 분리 |
| `0x4a1dac` | 데이터셋·입력 검사와 여러 경고 경로 | 입력 검증 경로, 알고리즘 핵심 수식으로 단정하지 않음 |
| `0x405ca4` → `0x4063d4` | 데이터셋 순회·수치 필드 처리와 후속 경로 | 보조 계산과 제어 흐름의 일부. 타입·함수 경계·간접 호출 복구 한계가 있음 |

역컴파일이 완료됐다는 것은 복구된 표현을 얻었다는 뜻이다. 원래 타입, 함수 경계, 동적 호출과 분기 의미를 모두 증명하지 않는다. 일부 함수에서 checksum 형태의 분기와 무한 루프 경고가 남아 있어 해당 표현을 원본 알고리즘의 완전한 의사 코드로 사용하지 않았다. 보호·라이선스·데모 검사를 우회하거나 수정하지 않았다.

공식 도움말과 설치 readme에서 확인한 외부 설정은 [동작 계약](smart2d-contract.md)에 따로 정리했다. 내부 정렬식·점수 가중치·동률 규칙·모든 배치 제약은 여전히 동일 복구가 입증되지 않았다.

## 등록한 새 계산 버전

`smart2d-v1`은 위 방향·수준 실행 계약을 참고해 Cutting에서 별도로 설계한 길로틴 휴리스틱이다. 방향별 분할과 정렬/배치 점수를 다르게 탐색하고, 기존 물리 절단·재질·두께·결·회전·재고 검사를 공유한다. 탐색 수는 그룹당 9/36/144개이다. 절단 계획 재탐색은 9·36·144개 경계의 최선 배치에만 적용하고 이전 경계의 최선 물리 결과를 보존한다. 후보마다 재탐색하던 초기 구현의 복잡 작업 지연을 이 방식으로 줄였다.

새 계산식이 더 우수하다고 선결정하지 않았다. [독립 입력 1,000개 백테스트](version-comparison.html)는 두 엔진에 같은 입력을 넣고 정밀 설정으로 2,000회 실행했다. 부재 종류별 배치 수량이 같은 721개에서 이용률 우세는 기존 235회·분석 버전 102회·동률 384회, 폐기 로스율 우세는 기존 373회·분석 버전 325회·동률 23회이다. 생산 결과가 다른 279개는 자재 승패에서 분리했고, 두 지표 우세가 엇갈린 247개도 따로 표시했다. 따라서 기본값은 기존 v1이며 새 버전은 사용자가 선택할 수 있는 실험 대안이다. 원본 EXE·메모리 사본·원본 UI 리소스·역컴파일 소스를 사이트에 배포하지 않는다.

분석용 프로세스는 작업 소유 Windows Job Object로 관리했고 사용 뒤 종료를 확인했다. 영구 설치된 REA·Ghidra·JDK와 사용자 프로그램·기존 데이터는 보존한다.
